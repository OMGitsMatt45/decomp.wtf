# Nintendo 64 projects

The app imports `.z64`, `.v64` and `.n64` cartridges, normalizes byte order and
splits their code and data. KMC GCC 2.7.2, IDO 5.3 EDG, IDO 5.3 classic cfront and
IDO 7.1 compile C/C++ on native Windows and Linux. Setup installs the pinned
tools; IDO requires its existing license acceptance. An AI agent is optional.

## Reviewed layouts

Automatic detection remains available. For overlays or TLB modules whose load
addresses you have established, select **Reviewed N64 layout** during browser
import. The JSON is checked against the SHA-256 of the normalized big-endian
cartridge before a project is created. Unknown addresses, overlapping cartridge
ranges and conflicting runtime extents fail explicitly.

```json
{
  "format": 1,
  "sha256": "REPLACE_WITH_NORMALIZED_CARTRIDGE_SHA256",
  "modules": [
    {
      "name": "main",
      "rom_start": "0x1000",
      "rom_end": "0x1810",
      "vram": "0x80000400",
      "text_end": "0x500",
      "sections": [
        {"offset": 0, "type": "code"},
        {"offset": "0x800", "type": "data"}
      ],
      "bss_size": "0x10"
    }
  ]
}
```

This example describes a layout, not a signature valid for any particular game.
Offsets and sizes accept JSON integers or hexadecimal strings. Each module has
an exclusive `rom_end`, a runtime `vram` and ordered sections beginning at offset
zero. Sections use `code`, `data` or `rodata`. BSS defaults to the end of the
decoded module; optional `bss_address` records a known gap before BSS.

Modules that share runtime memory must specify the same `exclusive_group`, such
as `"scenes"`. Their function/data labels carry the module name. Select those
functions by name when an address belongs to multiple overlays. Local claims
and memory reads use the selected module. Reviewed-layout projects currently
support local work and exports; room sharing is blocked because its existing
protocol cannot transfer these layouts and distinguish overlapping modules.

For a compressed module, add `compression` (`yaz0`, `deflate-1172` or
`deflate-1173`) and the exact `decoded_size`. Its section offsets refer to the
decoded bytes. Each decode is limited to 32 MiB and the complete analysis image
to 256 MiB. TLB virtual addresses are accepted as reviewed load addresses; the
importer does not infer the game's TLB setup.

The CLI uses the same database and importer:

```console
decompnet --db workspace.db n64 inspect game.z64 --layout layout.json
decompnet --db workspace.db n64 import game.z64 --layout layout.json --workspace projects --own-copy
decompnet --db workspace.db n64 export PROJECT_SLUG --workspace projects
```

Omit `--layout` on import for automatic detection. Importing the same cartridge
with different reviewed metadata creates a separate project. A failed layout
check creates no project.

## Matching reconstruction

Browser **Source → Matching reconstruction** and the default CLI export produce
a standalone project. Keep your original cartridge privately as `baserom.z64`.
Run `python build.py` to regenerate extracted assembly/assets and verify the
source-built image against every original byte. Recovered C/C++ functions also
undergo strict instruction, relocation and owned-data checks on each build.
Windows CRLF edits and nested headers are normalized in private compiler staging;
the original source files keep their authored line endings.

For compressed code, exports retain the original stored streams and regenerate
private decoded views in `analysis.z64`. The build verifies all decoded code
before emitting the original cartridge as `build/game.z64`. Changed decoded
code fails. This provides an exact container reconstruction; arbitrary modified
compressed streams are not recompressed. Cartridge bytes, decoded views,
extracted code and build products are ignored by the exported Git project.

## Shiftable source builds

Choose **Shiftable source project**, or pass `--format shiftable` to `n64 export`,
to create a separate `source-shiftable` directory. Matching reconstruction stays
available in both formats. This initial shiftable format supports one
uncompressed resident module, with an explicitly reviewed `text_end` and a zero
reserve between that offset and the first pinned data section. `text_end` is an
offset from the module start, not an address or a guessed function boundary.

```console
python build.py inventory
python build.py mod
```

Both commands first prove the original assembly rebuild. `inventory` reports
real ELF fixups, aliases, hazards and the available growth budget in
`build/relocations.json`. Edit function `.cpp`/`.c` sources, then use `mod` to
place them in order, resolve calls and function pointers and write
`build/mod.z64`. `build/shiftable-result.json` records function addresses, size
changes and the output hash. The actual JAL targets and data-pointer updates are
tested for each compiler family.

Function sizes may grow or shrink within the reviewed window. The first
function, cartridge entry, data, BSS and cartridge file extents stay pinned.
Moving source objects must start with the selected function and cannot add
owned data/BSS. Reference existing pinned globals instead. Unsupported ELF
relocations, fixed pointers/jumps into moving code, fixed cross-function branches,
aliases into changed function interiors and exhausted reserve stop the build.
Reviewed function boundaries must include their MIPS delay slots.
The inventory audits aligned references; it does not prove arbitrary opaque
data formats or self-modifying code safe to move. Review the game's indirect
references before using the result.

The builder identifies a standard CIC from IPL3 or the original checksum pair,
then updates CRC1/CRC2 for the modified cartridge. For an independently
established CIC, pass `--cic 6101`, `6102`, `6103`, `6105` or `6106`. Unknown CICs
require an explicit selection. Checksum reference tests cover all five families.

Compressed modules, multiple resident modules and mutually exclusive overlays
use the matching format. Editing original disassembly is outside the shiftable
baseline contract: its assembly must continue to rebuild the original first.

## C++ dependencies and runtime

Classic cfront prelinking now invalidates cached template objects when project
or include-file content, flags or compiler manifests change, even when source
timestamps are old or unchanged. A failed re-instantiation preserves the last
successful combined output. Recompile caller translation units yourself after
changes affecting their class layouts or inline code.

Heap allocation, virtual tables, local statics and array construction are
compiled by each original frontend. Their period target-runtime imports remain
explicit. Supply the game's compatible allocation, vector and startup code when
linking them. The app preserves C++ operator linkage and does not supply an IRIX
application environment or replace the target runtime with host C++ libraries.
See [IDO C++](ido-cpp.md) for the separate-project prelink command.

The [N64 qualification workflow](../.github/workflows/n64.yml) installs the four
compiler paths and runs matching, clean exports, layouts, source growth,
dependency failures, browser/CLI workflows and native worker teardown separately
on Windows and Linux. Missing required tools or skipped required tests fail CI.
All committed cartridge fixtures are generated from original test code.
