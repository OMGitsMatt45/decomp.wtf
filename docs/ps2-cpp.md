# PS2 C++ game output: Linux support, Windows blocked

PS2 projects using `ee-gcc-2.96` default to genuine C++ drafts, matching and
`.cpp` exports on Linux x86-64. `compiler.language = "c"` retains C, and older
exports without a language field remain C. **Native Windows EE-GCC 2.96 is
unavailable.** This release does not complete the Windows portion of the conversion.

## Original compiler and compatible tools

The existing pinned [decomp.me compiler archive](https://github.com/decompme/compilers/releases/download/compilers/ee-gcc2.96.tar.xz)
contains the original `ee-gcc` driver, preprocessor, C frontend, **C++ frontend**
`lib/gcc-lib/ee/2.96-ee-001003-1/cc1plus`, and EE assembler. Its SHA-256 is
`0590d2ca9da8f5903889d66761220d14b47a8d14ba987ca53db84a1650a1fd0a`.
The driver identifies itself as **`2.96-ee-001003-1`**. Compilation selects
`-x c++ -fno-exceptions -fno-rtti -fconserve-space`; there is no replacement
compiler, renamed C unit, modern preprocessor or C fallback. A missing C++
frontend is an error.

The programs are Linux i386 ELF binaries. The normal Linux bubblewrap sandbox
mounts the pinned `runtime-i386` loader and libraries; native compilation outside
that sandbox needs the host's 32-bit glibc (Ubuntu: `sudo apt install libc6-i386`).
Original EE assembly has both REL and RELA sections; exported linking uses the
pinned compatible GNU `binutils-mips`, rather than LLD. That binutils package
requires glibc 2.38 or newer, such as Ubuntu 24.04 x86-64.

```sh
decompnet toolchain install ee-gcc-2.96
decompnet toolchain install binutils-mips
decompnet toolchain install m2c
```

## Language, linkage and matching

This is the period GNU C++ dialect: templates, classes, local constructors,
references and explicit overloads are tested. Exceptions and RTTI are disabled.
No modern standard library, C++ startup, global dynamic initialization support
or `new`/`delete` runtime is supplied. Runtime-dependent code needs the game's
actual runtime support.

Plain game functions, prototypes and external variables keep C linkage.
Classes, templates, static helpers and explicit `extern "C++"` declarations
retain their authored linkage. The judge and exported builds use the same rules.
`-fconserve-space` retains common storage for the context's small-global
uninitialized declarations across exported translation units. m2c drafts use
`mipsee-gcc-c++`.

C++ source can compile differently from equivalent C. The C-built demo matches
all thirteen game functions as C++, including a template class in `abs_s32`.
Its null macro becomes `0`, and `!(flags & mask)` in `entity_spawn` is authored as
`(flags & mask) == 0` to recover the C instruction sequence. Submitted bodies are
not automatically rewritten to achieve matching.

Matching still requires exact instructions, resolved call/HI16/LO16/GP
relocations, and referenced owned data. Exported full builds and `build.py check`
run those same checks before linking: keeping original data in assembly cannot
conceal a changed compiled table or initialized small global.

Exports rebuild the flat payload as `build/game.bin`. New exports also keep the
owner's original main executable privately as `baserom.elf` and reconstruct
`build/game-ps2.elf` from rebuilt allocated sections, preserving original ELF
headers, padding and nonallocated metadata. Both outputs must match byte for
byte. The ELF envelope is retained from the input, not regenerated by the period
linker. Disc images and separate overlay files are not repacked.

## Precise Windows blocker and alternatives

A separate [native x86 ELF-host experiment](../tools/ps2_cpp/elf_host/README.md)
now runs the exact original compiler instructions in Win32 executables with
libc/process ABI adapters. Its initial full-pipeline parity corpus passes under
wibo on Linux. Native Windows execution and application/export integration have
their own gates; this research backend is not registered or selected by the app.
This does not recover the missing source or change the production status above.

The subsequent [source reconstruction experiment](ps2-cpp-reconstruction.md)
built Linux ELF32 and Windows PE32 frontends from available sources, but its
C++ corpus failed on both candidates. It does not supply a compatible native
Windows backend; reproducible recipes and measured failures are preserved.

See the [source/Windows acquisition investigation](ps2-cpp-source-search.md) for
verified hashes of a mislabeled Windows candidate and the inspected user upload.
The upload recovers Sony's incremental patch and build configuration, but its
`sce/ee/gcc/src/` directory is empty: the matching GNUPro EE base source archive
`src/src.tar.gz` is still missing. Its compiler frontends are the same Linux
ELF32 binaries already pinned here; there is no native Windows executable.

The exact 2.96 archive contains **Linux ELF32 programs only**, not Windows PE
executables. No matching Sony EE-patched 2.96 source or original native Windows
2.96 distribution was found in the investigated public packages/repositories.
The separate `ps2_compilers.tar.xz` collection was also inspected (SHA-256
`f337a65a4fbab5cf0e335efe266dcbc7cf69b19c665c6b3a8924736df151a02a`):
it contains Windows 2.95-family and Metrowerks tools, with no 2.96 entry.
This prevents a verified Windows source port of the original C++ frontend and
backend. The recovered patch assumes existing `2.96-ee-001003` EE support and
updates it to `2.96-ee-001003-1`; it does not supply the entire EE port. General
GNU GCC sources from October 2000 do not contain Sony's exact EE target patches.

Concrete alternatives investigated:

| Path | Evidence and limitation |
| :-- | :-- |
| Port the available EE source to Windows | [SSXModding source at `b595ded6`](https://github.com/SSXModding/ps2-ee-toolchain/blob/b595ded606227e93b8c4a447446c1d2ac093827d/ee/gcc/version.c) identifies itself as `2.9-ee-991111`; GirianSeed/aap archives and the [new macOS port](https://github.com/KevinParnell/ee-gcc-macos) are also 2.9-era. This can support a separately identified 2.9 toolchain, not 2.96 games by substitution. |
| Use existing Windows SN ProDG | decomp.me packages include 2.95.3-136 with a C++ frontend. It is a different compiler/backend and cannot establish 2.96 byte parity. It would need its own explicit toolchain and matching tests. |
| Run original Linux 2.96 through emulation/container tooling | [decomp-compat-kit](https://github.com/LinuxJessi/decomp-compat-kit) and [recompile-toolchains](https://github.com/maci0/recompile-toolchains) retain original Linux binaries in Docker/QEMU. They do not provide a native Windows compiler. An explicit emulator could avoid WSL but would still be emulation, requiring Windows process, filesystem and parity validation. |
| Statically recompile the exact Linux binaries | Could preserve compiler identity without missing source, but would require an i386 ELF translator and Linux/libc compatibility layer for the driver and its children. No working verified Windows package was located; the SGI/MIPS IDO translator cannot directly translate these i386 programs. |
| Obtain exact 2.96 source or an authentic Windows build | Preferred path to complete native Windows support; then build/audit its process support and verify code, relocations and full exports against the original Linux compiler. |

A direct comparison of `ee-gcc2.9-991111.tar.xz` (SHA-256
`99cb5db603cd985b50fc6851157020ad69489f2227309ccf825bd43ac7bc19dd`)
with the pinned 2.96 compiler on `tests/fixtures/ps2_cpp_features.cpp` at `-O2 -G8`
found different function code/relocations for the template, floating-point and
constant-table probes (three of seven functions). Even this small fixture rules
out treating the available 2.9 source as an exact 2.96 replacement.

Windows availability checks fail explicitly and never start WSL or select 2.9,
SN, modern GCC or Clang automatically. Existing native Windows support for the
other consoles remains available. Classic IDO 5.3 investigation and PlayStation
PR #2 remain separate.

## Verification

`DECOMP_TEST_PS2_CPP=1 python -m pytest -q tests/test_ps2.py tests/test_ps2_cpp.py`
requires the pinned EE compiler, MIPS binutils, m2c and prepared homemade zlib
sources (`python projects/zlib-n64/prepare.py`). Required Linux CI fails on skips.
Tests cover C++-only syntax and `__cplusplus`, rejection by C, original code and
relocation snapshots, invalid C++ errors, missing frontend errors, C++ m2c drafts,
all thirteen C-built game functions, changed instructions/calls/GP references,
complete owned tables and small data, per-unit headers, paths with spaces, clean
C/C++ exports after deleting generated files, and Git `core.autocrlf=true`.
A separate Linux check compiles with the original driver inside bubblewrap.

Windows CI verifies the explicit unavailable-toolchain error without WSL; it
**does not claim actual native Windows PS2 C++ compilation or rebuilds**.

The [native Linux validation run](https://github.com/OMGitsMatt45/decomp.wtf/actions/runs/39341473279)
checks the implementation in `998cb672843735e8e5e2ee0e0869ad17fb6f275e`:
**17 PS2 tests passed with zero skips** on Ubuntu 24.04 x86-64, and the original
C++ driver also passed the separate Ubuntu 22.04 bubblewrap check with the
pinned i386 runtime. Linux CI installs the compiler in a path containing spaces.

All five jobs in that run passed, including the broader native Windows/Linux
regressions for N64, IDO, GBA and PS1. The native Windows platform checks include
the explicit PS2 unavailable-toolchain error; they do not compile PS2 output.
