# Nintendo 64: reviewed layouts and bounded shiftable exports

Status: **implemented; expanded native Windows/Linux qualification pending**.
PR #3 extends the existing KMC GCC 2.7.2, IDO 5.3 EDG/classic cfront and IDO 7.1
paths. The [user guide](../n64.md) describes the supported workflows and limits.

## Implemented

- [x] Hash-bound reviewed module layouts, mutually exclusive overlays, TLB load
  addresses, code/data boundaries and explicit BSS placement.
- [x] Original cartridge provenance for automatically unpacked code and reviewed
  Yaz0/Rare deflate modules. Clean matching exports verify decoded code and the
  source-built original cartridge; edited decoded code fails verification.
- [x] Shiftable exports link resident modules and exclusive overlays independently
  with a reviewed text end and growth reserve per module. They prove the original
  baseline, inventory ELF fixups, resolve cross-module calls/data pointers, update
  CIC checksums and reject unresolved references or overflow.
- [x] Edited reviewed Yaz0, Rare 1172/1173 and gzip modules recompress into their pinned
  storage allocations and decode back to the linked bytes before output is accepted.
- [x] Per-function compiler, optimization, language and frontend settings, shared
  by matching, drafts, regressions and clean standalone builds in one project.
- [x] Content-based classic template invalidation across transitive headers,
  including unchanged timestamps, invalid templates and atomic output retention.
- [x] C++ operator ABI correction and period runtime fixtures for heap allocation,
  virtual dispatch/destruction, arrays and local statics across all four paths.
- [x] Browser and CLI import/export flows, module-specific local claims, ambiguous
  address rejection and explicit failure reporting.
- [x] Reviewed-layout rooms transfer hash-bound metadata and synchronize functions,
  data names, profiles, unit headers and notes by module/ROM identity, including
  overlays sharing RAM. Cartridge bytes and assembly remain local.
- [x] Retail-scale links use response files and exact filename patterns to avoid
  Windows command limits and repeated GNU ld filename searches. Explicit CLI
  optimization profiles create separate projects when their compiler settings differ.
- [x] Startup relocations retain boot-code BSS facts even when heuristic size
  detection is incomplete. Code discovered inside a resident data region preserves
  its parent load/BSS bounds. External automatic labels retain their encoded addresses.
- [x] Required native qualification workflow with a no-skips gate, original
  fixtures, clean standalone builds and native worker teardown on both hosts.

## Qualification

- [x] Previous native Linux baseline: 136 required checks, no skips.
- [x] Previous native Windows baseline: 136 required checks, no skips.
- [x] Expanded local suite: 167 passed, no skips, using native IDO compilers and
  the KMC compatibility harness.
- [ ] Expanded native Windows/Linux CI: dispatch currently returns an
  Actions-disabled error; the local run does not replace native qualification.
- [x] Local fixture tests cover actual source size changes, linked JAL targets,
  function-pointer updates, preserved globals and exhausted reserve.
- [x] Independent released checksum reference vectors cover CIC 6101/6102,
  6103, 6105 and 6106.

Local compatibility execution of the original Linux KMC i386 tools does not count
as native Linux qualification. The required CI job installs their native package
and its i386 system runtime. Existing original-IRIX compiler/relocation reference
checks remain required for each relevant frontend.

The [previous native run](https://github.com/OMGitsMatt45/decomp.wtf/actions/runs/39873662417)
tested implementation commit `4fff497ce901b715795e6d2495e97052b15a2761`.
The [validation record](../n64-validation.json) pins those jobs and distinguishes
the expanded implementation's local results and outstanding native checks.

Private testing verified clean, byte-identical cartridges for Super Mario 64,
Star Fox 64 revision 1, Ocarina of Time revision 2, Majora's Mask and Donkey Kong 64:
116 MiB in total, retaining 69 accepted small C++ functions. Super Mario 64's 54
functions build together with per-function `-O2` and `-O0` profiles. The
[retail validation record](../n64-retail-validation.json) contains metadata,
hashes, the regeneration procedure and scope. These automatic retail layouts
lack reviewed growth reserves; retail shiftable builds and playthroughs are not
qualified by these checks.

## Boundaries

Moving modules need reviewed text boundaries and a zero code reserve. Compressed
edits need reviewed codecs and fixed cartridge allocations; automatic joined pages
are not treated as a known storage layout. Opaque references and loader tables
still require game-specific review. The first function, data/BSS, entry and file
extents remain pinned; moving source cannot introduce new owned data/BSS.
Reviewed rooms require the module-aware protocol. C++ fixtures expose target
runtime imports; no IRIX application environment or host-runtime substitution is supplied.

No commercial ROMs, SDK payloads, BIOS files or keys are included. See the
[roadmap](../future-work.md) and [native qualification workflow](../../.github/workflows/n64.yml).
