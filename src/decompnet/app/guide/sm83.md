# Game Boy / Game Boy Color assembly

Work in RGBDS SM83 assembly. A claim is a discovered byte range, not proof of a
routine boundary. `context.inc` contains shared numeric constants and is included
automatically. Keep the candidate's SECTION, storage bank, CPU address, size, and
exported label. Submit one section at a time with `compile_and_diff`.

Bank `01:4000` and `02:4000` contain different bytes. The database also exposes a
unique address key `(bank << 16) | CPU`, but CPU operands remain 16-bit addresses.
Known external labels are linked at their actual banks and CPU addresses, so
`call label` and `BANK(label)` work. The judge rejects any extra nonempty section,
wrong placement, wrong size, undefined reference or differing encoded operand.
It never masks relocations. This workflow does not generate C/C++ or run m2c.

Use `rename_symbol` when you understand a label. `split_function(function, at,
new_name)` accepts `at="02:4000"` to discover a known entry in another storage
bank, or an instruction boundary inside an unverified range to split it. It does
not emulate mapper state. Do not guess the target bank of a ROM0 jump to $4000.
Register-mediated switches, MBC1's lower window, jump tables, interrupts and RAM
code still need analysis; leave notes for the next person.

Submissions are self-contained instructions and numeric definitions. File
INCLUDE/INCBIN, EQUS, macros, interpolation and escapes are disabled. Use explicit
bytes for undocumented encodings only after reviewing their purpose. Verification
counts reviewed assembly bytes, not a C/C++ decompilation or a completed game.
