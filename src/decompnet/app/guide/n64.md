# N64 facts that help

Memory
- 0x80000000-0x807FFFFF: RAM (KSEG0, cached). 0xA0000000+: the same RAM uncached (KSEG1).
- 0xA4000000-0xA4FFFFFF: hardware registers (video VI 0xA4400000, audio AI 0xA4500000, peripheral PI
  0xA4600000, serial SI 0xA4800000). Code that pokes these is driver/OS code.
- The game's code is loaded from the ROM to RAM at boot (the "main" segment). Big games load more code
  later. The app detects additional uncompressed and supported compressed code
  ranges. Reviewed layouts can supply known module boundaries, load addresses,
  mutually exclusive overlays and TLB mappings. Detection remains heuristic:
  review questionable function boundaries before recovering their source.

The OS library
- Games link Nintendo's OS library (libultra): threads, message queues, DMA, controller input, the
  scheduler. Its functions use recognizable patterns (disabling interrupts with `mfc0`/`mtc0`, TLB and
  cache instructions). Matching those needs the exact library version; game code first is a better use
  of time.

Graphics and audio
- Display lists are arrays of 64-bit commands built in memory: long runs of stores of constants with
  0xE7000000, 0xFD..., 0x06000000-like high words are display list building, usually through macros.
- Audio and graphics microcode (RSP code) is data, not MIPS code you decompile.

Compilers
- First-party games mostly use IDO (5.3 for early titles, 7.1 later). Many third-party games use GCC
  2.7.2 from KMC. A few use SN Systems' GCC variants.

C++ output
- KMC ROM projects use the period GCC 2.7.2 C++ frontend, with exceptions and RTTI disabled.
- Keep original game entry points and external game declarations at C linkage (`extern "C"`);
  the judge and export add this for plain global functions. Classes, templates and C++ helpers
  retain C++ linkage. Use features supported by that compiler, without host standard headers.
- The same C expression can generate different code as C++. For an absolute value using a
  branch-likely instruction, try `if (value < 0) value = -value; return value;` rather than a ternary.
  If the target uses a sign mask, try `s32 sign = value >> 31; return (value ^ sign) - sign;`.
- A pointer declared inside a loop can change this frontend's loop optimization. If a C-style
  loop differs, try declaring the pointer before the loop and assigning it inside.
- IDO 5.3/7.1 projects use their original SGI/EDG C++ frontend through `NCC`, with the original IDO
  optimizer, code generator and assembler. Its period dialect differs from KMC's. Do not use host
  standard headers or assume modern C++ features and runtime libraries are available.
- `project_info` reports the source language and selected IDO frontend. IDO 5.3
  defaults to SGI/EDG and also supports the explicitly selected classic cfront
  frontend; both retain the original 5.3 backend. Never switch a 5.3 project to
  7.1 just to accept C++ syntax: the generated bytes can differ. Cross-unit classic
  templates use the separate `decompnet.ido_prelink` command described in docs/ido-cpp.md.
- A function can override the project's toolchain, flags, language and frontend.
  Read its compiler details before recovering it; use the `decompnet n64 profile`
  console command to select a profile. Matching and standalone exports use the
  same settings. Room profiles are chosen by the host and synchronized to members.
